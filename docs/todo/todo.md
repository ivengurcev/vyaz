**Репозиторий:** https://github.com/ivengurcev/vyaz  
**Ветка:** `dev`  
**Коммит:** `a84d51e`

Анализ выполнен по исходному коду. Полноценное тестирование приложения и сборки не проводилось, поэтому некоторые проблемы требуют воспроизведения.

## 1. Повторный анализ исходников при каждом SSR-запросе

**Приоритет:** средний  
**Файл:** `server/collectRouteInitialData.mjs`

### Проблема

При обработке SSR-запроса вызывается `collectRouteInitialData()`, который:

1. Читает исходный файл компонента.
2. Рекурсивно обходит его локальные импорты.
3. Ищет обращения к `initialData`.
4. Сопоставляет найденные ключи с API.
5. Выполняет внутренние запросы.

Этот процесс повторяется при каждом обращении к странице.

### Последствия

- Лишние файловые операции при каждом SSR-запросе.
- Увеличение времени ответа.
- Зависимость production runtime от доступности исходных файлов приложения.
- Дополнительная нагрузка при параллельных запросах.

### Предлагаемое решение

Перенести обнаружение зависимостей на этап сборки.

Для каждого маршрута генерировать список необходимых данных:

```js
{
    path: '/profile',
    initialDataKeys: ['userProfile', 'settings']
}
```

Во время SSR использовать готовый список.

**Альтернатива для ближайшего этапа:** кеширование результата анализа в памяти. Это проще, но потребует инвалидации при изменении файлов в режиме разработки.

## 2. Отсутствие обновления initialData при клиентской навигации

**Приоритет:** высокий при использовании `initialData`  
**Файл:** `Layout/ApplicationCore.jsx`

### Проблема

При первоначальном запросе сервер подготавливает `initialData`.

Но при переходе:

```js
navigate('/another-page')
```

клиентский роутер только загружает новый компонент и обновляет текущий путь.

Данные нового маршрута не запрашиваются, а значение `initialData` остаётся прежним.

### Сценарий

1. Пользователь открывает `/articles`.
2. SSR загружает список статей.
3. Пользователь переходит на `/profile`.
4. React загружает компонент профиля.
5. Компонент получает `initialData` предыдущей страницы.

### Последствия

- Отсутствие необходимых данных.
- Возможное отображение устаревшей информации.
- Разное поведение страницы при прямом открытии и клиентском переходе.

### Предлагаемое решение

Определить единый контракт загрузки данных для SSR и клиентской навигации.

Необязательно сразу создавать собственный аналог React Query. Возможен простой механизм загрузки данных маршрута при переходе.

## 3. Хрупкий поиск initialData через регулярные выражения

**Приоритет:** средний  
**Файл:** `server/collectRouteInitialData.mjs`

### Проблема

Зависимости от данных обнаруживаются регулярным выражением:

```js
/initialData(?:\?\.|\.)\s*([A-Za-z0-9_]+)/g
```

А импорты обнаруживаются отдельными регулярными выражениями.

Такой подход покрывает только часть возможного синтаксиса JavaScript.

### Сценарии

Обращение:

```js
initialData['userProfile']
```

не будет обнаружено.

Деструктуризация:

```js
const { userProfile } = initialData;
```

также не будет обнаружена.

При этом совпадения внутри комментариев и строк могут ошибочно восприниматься как реальные зависимости.

### Последствия

Автоматическая загрузка данных может неожиданно не сработать либо выполнить лишний запрос.

### Предлагаемое решение

Для начала явно документировать поддерживаемый синтаксис.

Если механизм будет активно использоваться, перенести анализ на этап сборки и рассмотреть разбор синтаксического дерева (AST).

## 4. Несогласованность авторизации и клиентской навигации

**Приоритет:** высокий  
**Файлы:** `Layout/ApplicationCore.jsx`, `server/router.mjs`

### Проблема

На сервере защищённые маршруты проходят проверку авторизации и `hasAccess`.

В клиентском `navigate()` аналогичной проверки нет.

### Сценарий

1. Пользователь открывает публичную страницу.
2. Вызывает клиентский переход на приватный маршрут.
3. Роутер загружает компонент без обращения к серверной проверке доступа.

### Последствия

Возможен показ интерфейса защищённой страницы неавторизованному пользователю.

Это не означает автоматического доступа к защищённым данным: безопасность API обеспечивается сервером. Однако UI-поведение становится несогласованным.

### Предлагаемое решение

Разграничение доступа к данным обязательно должно оставаться серверным.

Для клиентской навигации предусмотреть обработку приватных маршрутов и перенаправление на авторизацию.

## 5. Возможная гонка при быстрой клиентской навигации

**Приоритет:** средний  
**Файл:** `Layout/ApplicationCore.jsx`

### Проблема

`navigate()` асинхронно загружает компонент маршрута:

```js
const nextComponent = await nextRoute.component();
```

Но не проверяет, остался ли этот переход актуальным.

### Сценарий

1. Пользователь переходит на страницу A.
2. Начинается загрузка компонента A.
3. Пользователь переходит на страницу B.
4. Компонент B загружается быстрее.
5. Затем завершается загрузка A.

В результате более старый переход может перезаписать состояние нового.

### Последствия

URL и отображаемый компонент могут перестать соответствовать друг другу.

### Предлагаемое решение

Добавить идентификатор навигации и применять результат только последнего актуального перехода.

---

## 6. Отсутствие обработки ошибок загрузки клиентского маршрута

**Приоритет:** средний  
**Файлы:** `Layout/ApplicationCore.jsx`, `builder/__bootstrap.js`

### Проблема

Динамические импорты компонентов выполняются без явной обработки ошибок.

### Сценарий

Браузер не может загрузить JavaScript-чанк из-за сетевой ошибки или изменения версии приложения после деплоя.

### Последствия

- Необработанный rejected Promise.
- Переход не завершается корректно.
- Пользователь не получает понятной реакции приложения.

### Предлагаемое решение

Добавить обработку ошибок динамического импорта.

Для первоначальной загрузки предусмотреть понятный fallback. Для клиентской навигации можно использовать обычный переход браузера при невозможности загрузить компонент.

## 7. Возможная ошибка гидрации при неизвестном клиентском маршруте

**Приоритет:** средний  
**Файл:** `builder/__bootstrap.js`

### Проблема

Во время гидрации выполняется:

```js
const initialRoute = router.resolve(window.location);

const InitialComponent =
    normalizeRouteComponent(await initialRoute.component());
```

Проверка существования `initialRoute` отсутствует.

### Сценарий

Сервер возвращает HTML для маршрута, которого нет в клиентском роутере, например маршрута с `isServer: true`.

`router.resolve()` возвращает `undefined`, после чего обращение к `.component()` вызывает исключение.

### Последствия

Клиентская инициализация не завершается.

### Предлагаемое решение

Явно определить поведение для серверных маршрутов.

Если `isServer` подразумевает отсутствие клиентского React runtime, гидрацию для таких страниц следует отключать либо предусмотреть соответствующий режим.

## 8. Неоднозначность сопоставления API с initialData

**Приоритет:** низкий–средний  
**Файл:** `server/collectRouteInitialData.mjs`

### Проблема

Механизм сопоставляет имя данных с API-путём.

Если точного совпадения нет, используется поиск маршрута по окончанию пути.

### Сценарий

В приложении существуют:

```text
/api/admin/profile
/api/users/profile
```

Компонент обращается к:

```js
initialData.profile
```

Оба эндпоинта могут подходить по завершающему сегменту.

Результат зависит от порядка регистрации API.

### Последствия

В компонент могут попасть данные не того эндпоинта.

### Предлагаемое решение

Для неоднозначных совпадений требовать явное сопоставление либо выдавать диагностическое предупреждение.

## 9. Недостаточное тестовое покрытие

**Приоритет:** средний  
**Каталог:** `test/`

### Проблема

Сейчас присутствуют два тестовых файла:

- `api.test.mjs`
- `router.test.mjs`

Они проверяют конкретные регрессии, но не покрывают большую часть интеграционного поведения фреймворка.

### Наиболее полезные следующие тесты

1. SSR и последующая гидрация.
2. Клиентская навигация между маршрутами.
3. Защищённые маршруты.
4. Автоматический сбор `initialData`.
5. Browser/SSR-сборка минимального приложения.

### Предлагаемое решение

Не стремиться к формальному проценту покрытия.

Добавлять интеграционные тесты на реальные сценарии, прежде всего на взаимодействие сборки, роутера и SSR.

## 10. Пакет пока зависит от структуры workspace

**Приоритет:** низкий для собственных проектов  
**Файлы:** `package.json`, `builder/workspaceCorePlugin.mjs`

### Проблема

Пакет использует собственный механизм разрешения путей `@vyaz/core`, но пока не содержит явно оформленной публичной карты экспортов (`exports`).

Также нет самостоятельного проверенного сценария установки нового приложения.

### Последствия

Работа в существующем workspace возможна, но перенос ядра в независимый проект может потребовать дополнительной настройки.

### Предлагаемое решение

Решать при появлении второго независимого потребителя или необходимости публикации пакета.

Сейчас это не блокирующая проблема.

## 11. Недостаточно точная документация окружения

**Приоритет:** низкий  
**Файлы:** `README.md`, `package.json`

### Проблема

Не все инструкции README можно выполнить непосредственно из каталога ядра.

В частности:

- команда `yarn lint` отсутствует в scripts самого пакета;
- установка `yarn add @vyaz/core` предполагает доступность пакета в реестре;
- требования к версии Node.js нуждаются в проверке;
- подключение через workspace не показано на полностью воспроизводимом примере.

### Предлагаемое решение

Документировать прежде всего фактически используемый сценарий разработки.

Не добавлять универсальный установщик или дополнительные CLI-команды только ради документации.

## Общая оценка

Критических доказанных уязвимостей при просмотре кода не обнаружено. При этом часть перечисленных проблем требует воспроизведения в работающем приложении.

Основные риски сосредоточены в двух областях:

**Клиентская навигация.** Пока она заметно проще серверного роутера и не обеспечивает полной согласованности данных, авторизации и состояния при переходах.

**Автоматическая загрузка данных.** Механизм интересный, но сейчас зависит от анализа исходников во время HTTP-запросов и соглашений об именовании API.

Перед масштабной переработкой ядра разумно проверить эти сценарии на существующем приложении. Остальные ограничения не требуют немедленного исправления.
